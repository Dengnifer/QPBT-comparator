# QPBT-comparator

Comparator challenge for the Lean 4 formalization of the **quantum Pauli basis test**
(the Pauli basis test section of the MIP\* = RE paper), developed in
[Dengnifer/MIPStarRE-A](https://github.com/Dengnifer/MIPStarRE-A).

The two headline theorems verified here are

- `MIPStarRE.QPBT.pauli_soundness` (`thm:pauli`), and
- `MIPStarRE.QPBT.pauli_soundness_qubit` (`cor:pauli-binary`),

checked in a single comparator run.

## Layout

- `Challenge.lean` — imports only Mathlib and re-declares, verbatim and in dependency order,
  every declaration in the statement closure of the two theorems, then states them with `sorry`.
  It is the entire human audit surface: a reader who agrees that this file states the intended
  theorems does not need to read anything else. Generated by `scripts/comparator/` in the library
  repository; every declaration carries a `-- source:` provenance comment.
- `Solution.lean` — imports the MIPStarRE-A library, pinned by commit in `lakefile.toml`, which
  proves the same statements under the same fully qualified names. No bridging lemmas.
- `comparator.json` — the comparator configuration: both theorem names, and `propext`,
  `Quot.sound`, `Classical.choice` as the only permitted axioms.
- `verify.sh` — runs the official [leanprover/comparator](https://github.com/leanprover/comparator)
  (real landrun sandbox, nanoda external kernel, `lean4checker` re-check). On macOS, where there is
  no Landlock, `./verify.sh --fake-landrun` runs the functional check without the sandbox.

## Running the check

```sh
./verify.sh                 # Linux, sandboxed, with the external kernel
./verify.sh --fake-landrun  # macOS or any host without Landlock
```

## Regenerating after a library change

`Challenge.lean` is generated, not hand-edited. After any change to a definition in the statement
closure, regenerate it in the library repository
(`python3 scripts/comparator/check_challenge_drift.py --root . --challenge qpbt --update`), copy
`scripts/comparator/expected/ChallengeQPBT.lean.expected` here as `Challenge.lean`, and bump the
`rev` pin in `lakefile.toml` to the library commit it was generated from. The library's CI fails if
the checked-in expected copy drifts from what the tooling produces.

The design follows the challenge repository of the companion low individual degree test
formalization, [LionSR/LDT-comparator](https://github.com/LionSR/LDT-comparator), and the Lean
reference manual's *Validating Proofs* chapter. The regeneration tooling and the trust model live
in the library repository (`scripts/comparator/`, `docs/comparator.md`).
